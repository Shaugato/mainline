6 · THE THREE lifecycle.precondition BLOCKS — ALL THREE PROVEN TO EVALUATE
════════════════════════════════════════════════════════════════════════════════════════

  The plan JSON's `checks` array reports `pass` with one instance for each of
  module.api.aws_lambda_function.this and module.api.aws_cloudwatch_metric_alarm
  .duration_p99, in both the committed and the fresh plan. "pass" alone does not prove a
  condition is live — a condition that is never reached also never fails. So each was
  perturbed in the scratch copy until it FIRED. All three did:

  (1) aws_lambda_function, main.tf:290 — package manifest architecture
      Perturbation: `-var lambda_architecture=x86_64` against the arm64 package.
      → Error: Resource precondition failed
        var.architecture is "x86_64"
        var.package_path is "../../../out/lambda/mainline-demo-api-arm64.zip"
        "…was built for a different architecture than var.architecture (x86_64)…"        LIVE

  (2) aws_lambda_function, main.tf:295 — package manifest handler
      Perturbation: scratch copy of mainline-demo-api-arm64.zip.json rewritten with
      handler = "wrong_module.wrong.handler".
      → Error: Resource precondition failed
        "…declares a handler other than mainline_demo_api.app.handler, which is what this
         function is configured to call."                                                LIVE

  (3) aws_cloudwatch_metric_alarm.duration_p99, main.tf:460 — threshold below timeout
      Perturbation: scratch module default duration_p99_threshold_ms 12000 → 15000.
      → Error: Resource precondition failed
        var.duration_p99_threshold_ms is 15000
        var.timeout is 15
        "…is not below the function timeout (15 s = 15000 ms). Lambda terminates the
         invocation at the timeout and the Duration datapoint is capped there, so this
         alarm could never breach - a control that looks present and is not."            LIVE

      Every perturbation was made in the scratch copy only and reverted. No file under
      D:/CoackroachDBxAWS/mainline/infra/ was modified at any point.

  Two further check entries deserve their status stated honestly, because "pass" is
  vacuous for both — they have ZERO instances under this variable set:
      module.api.aws_lambda_permission.cloudfront_invoke   pass, 0 instances (count = 0)
      module.site.aws_cloudfront_distribution.site         pass, 0 instances
      module.site.aws_s3_bucket.site                       pass, 0 instances
  The cloudfront_distribution_arn precondition at main.tf:367 is therefore NOT exercised by
  this plan. That is correct behaviour for url_authorization_type = "NONE" — it is only
  worth knowing so nobody cites it as a control that was checked here.
