# CLOUD-40001 — what a multi-node cluster does, what this wave proved, and what is still unproven

**Written 2026-08-14 by worker W6** (lead plan: `docs/leads/judge-can-sign-plan.md`, ruling
**R6** and ruling **R7**). Local `HEAD` `eefae1c`, working tree **dirty** — this wave was
mid-flight when these numbers were taken, and §6 says exactly which parts of it had landed.

---

## 0 · The paragraph a reader in a hurry needs

> **`40001 RETRY_SERIALIZABLE` was reproduced HERE, on the single-node local cluster, six
> times out of six deliberate races.** The premise this work was commissioned under — that
> CockroachDB Cloud returns `40001` under contention *that single-node Docker never
> produces* — is **false as stated**, and the correction makes the work harder rather than
> easier: it removes the excuse "this cannot be tested without Cloud" and replaces it with
> a control that actually fires. The retry guards in this tree are therefore proven
> **necessary and effective against a real `40001`**, not against a mocked one.
>
> **This wave did NOT run the suite against CockroachDB Cloud.** Not once. The Cloud DSN is
> a GitHub repository secret and is not present on this workstation; no result against Cloud
> is reported here, inferred here, or interpolated here. What Cloud adds is **rate** and
> **variety**, and neither has been observed. A green on one local node is evidence about
> one local node and is not offered as evidence about anything else in this document.

## 1 · What a multi-node CockroachDB does that a single node does not

A single-node `start-single-node` cluster and CockroachDB Cloud Basic run the same SQL and
the same isolation level. What differs is the set of *reasons* a transaction can be told to
start again, and how often it is told.

| | single node, this workstation | CockroachDB Cloud Basic (Singapore) |
|---|---|---|
| ranges | one replica, one store, one process | replicated across nodes |
| clock | one clock; there is nothing to disagree with | many clocks, bounded by `max_offset`; a read may land inside the uncertainty interval and be restarted |
| `RETRY_SERIALIZABLE` | produced by a **constructed** read-write cycle (§2) | produced by construction **and** by ordinary concurrent traffic |
| `RETRY_WRITE_TOO_OLD` | observed here, from a **local** write pushing a timestamp | also arises from a *follower's* clock, which has no local analogue |
| `ReadWithinUncertaintyInterval` | **not reachable** — there is no second clock | reachable, and it is a distinct restart reason |
| latency per statement | loopback, microseconds | a runner in `ubuntu-24.04` to Singapore, per round trip |
| contention window | narrow, because statements are fast | wider, because every statement is slower — the *same* code holds locks for longer |
| `gc.ttlseconds` | `14400` by default | `4500` — the local node is the **more permissive** exam |
| privileges | `root` | `mainline-sql`, already observed being refused `42501` (§5) |

The row that matters most is the second-to-last. Cloud does not mainly add *new* errors; it
widens the window in which the *existing* ones happen, so a transaction that has never lost
a race on a laptop can lose one routinely in Singapore. That is why "we never saw a `40001`
in CI" was never evidence that the retry loops were unnecessary.

## 2 · What this wave PROVED, with the numbers

### 2.1 A real `40001`, six of six, measured by W6 on this workstation

Scratch database `w_w6`, created for this measurement and **dropped afterwards**. Two
connections, two rows: A reads key 1 and writes key 2, B reads key 2 and writes key 1.
Neither can be ordered before the other.

```
round 1: sqlstate=40001 RETRY_SERIALIZABLE=True
round 2: sqlstate=40001 RETRY_SERIALIZABLE=True
round 3: sqlstate=40001 RETRY_SERIALIZABLE=True
round 4: sqlstate=40001 RETRY_SERIALIZABLE=True
round 5: sqlstate=40001 RETRY_SERIALIZABLE=True
round 6: sqlstate=40001 RETRY_SERIALIZABLE=True

version                        : CockroachDB CCL v26.2.5 (x86_64-pc-linux-gnu,
                                 built 2026/07/28 18:56:00, go1.25.5)
default_transaction_isolation  : serializable
rounds                         : 6
rounds_with_40001              : 6
rounds_with_RETRY_SERIALIZABLE : 6
```

First message, verbatim and truncated:

```
restart transaction: TransactionRetryWithProtoRefreshError: TransactionRetryError:
retry txn (RETRY_SERIALIZABLE): "sql txn" meta={id=137aee03 key=/Table/32039/1/2/0
iso=Serializable pri=0.00287797 ep…
```

This is an independent reproduction. The lead measured the same 6-of-6 under ruling R6, and
W4 measured it a third time over the product's own tables. **Three independent
reproductions on one node.** The claim that a single node "never produces" `40001` is
retired.

### 2.2 The guard is exercised by a control that fires — not by a mock

`docs/diagnosis/retry-negative-control.md` (W4) records the census over the product's real
seed-a-permit shape:

```
[control] unguarded census over 6 races: {'40001': 6, '00000': 6}
[control] guarded:                       12 commits, 6 retried 40001(s)
```

Unguarded, six of six races lost a whole history — a recall run, a Proof of Exhausted
Recall, an obligation, the exposure receipt and the line binding them. Guarded through
`trappoint_testkit.txn.run_txn` over `trappoint_core.retry.run_gate`, **twelve of twelve
callers committed** and the six `40001`s were *spied* being retried rather than assumed.
Re-run by W6 for this document:

```
pytest packages/trappoint-testkit/tests/test_txn.py \
       tests/concurrency/test_seed_permit_needs_retry.py --crdb=reuse -q

junitxml: tests=19  failures=0  errors=0  skipped=0  time=98.792s
```

W4 also observed **both costumes of `40001` locally** — `RETRY_SERIALIZABLE` and a
`WriteTooOldError`. Both carry SQLSTATE `40001`; a client discriminating on the *message*
would have got one of them wrong. `trappoint_core.retry` discriminates on the code.

### 2.3 The unguarded path flakes on ONE node, unprovoked

This one was not constructed. During W6's baseline run of the demo-api suite — no race
planted, no contention arranged — `_seed_permit` raised a real serialization failure:

```
verticals/mainline/apps/demo-api/tests/test_transitions.py:225: in _seed_permit
E   psycopg.errors.SerializationFailure: restart transaction:
    TransactionRetryWithProtoRefreshError: TransactionRetryError:
    retry txn (RETRY_SERIALIZABLE - failed preemptive refresh)
```

At the moment of that run `_seed_permit` committed roughly twenty-nine statements with **no
retry**. It had been predicted to "flake in the environment that matters"; it flaked in
**this** one, on one node, today.

**This is the strongest single argument in this document**, and it is an argument about
method rather than about CockroachDB. The guard was not added because a multi-node cluster
was imagined to need it — it was added because an unguarded transaction was **watched
losing a race on the machine that was supposed to be too simple to produce one**. W5 has
since wrapped it: `test_transitions.py:312` runs the whole transaction through
`trappoint_testkit.txn.run_txn` over `trappoint_core.retry.run_gate`, from `BEGIN`, on a
fresh connection per attempt — never a statement, which `spec/errors.md` §2.1 forbids. §6
records that W5 landed *after* the measurement above, which is the order that makes the
measurement evidence rather than decoration.

**And the repair is measured, not assumed.** Counting `_seed_permit` frames carrying a
`SerializationFailure` across the two `--junitxml` documents in §6:

```
BEFORE (11:17, unguarded) : 1
AFTER  (11:39, guarded)   : 0
```

One node, one unprovoked `40001`, one guard, and the error is gone from the report. **What
that does not establish is anything about Cloud** — see §3.

## 3 · What this wave did NOT prove

**This wave did not run the demo-api suite, or anything else, against CockroachDB Cloud.**

Measured rather than assumed: no `CRDB_CLOUD_DSN`, `MAINLINE_*`, `COCKROACH_*`,
`TRAPPOINT_*` or `CLOUD*` variable exists in this environment — `Get-ChildItem Env:`
filtered on those names returns a count of **0**. `.github/workflows/cloud-verify.yml` binds
the DSN from `secrets.CRDB_CLOUD_DSN`, which is reachable by CI only. A Cloud cluster
demonstrably exists: `console/fixtures/bundles/demo-cloud/sql/cluster-fingerprint.txt`
records database `mainline_demo`, user `mainline-sql`, CockroachDB CCL v26.2.5 — with
`cluster_id` and `node_locality` recorded as `(refused: 42501)` rather than omitted, because
a missing line and a refused line are different facts. Its credential is not on this
workstation, and no attempt was made to obtain one.

So the following are **UNPROVEN**, and none of them is covered by anything in §2:

1. **The RATE.** How often `40001` arises in this product's *ordinary* traffic against a
   multi-node cluster. Every rate in §2 is the rate of a race someone constructed on
   purpose, plus one unprovoked flake. A rate is a property of the platform and the
   workload together, and this workload has never met that platform.
2. **The VARIETY that has no local analogue.** `ReadWithinUncertaintyInterval` restarts
   cannot occur on one node — there is no second clock to disagree with. Neither can a
   `RETRY_WRITE_TOO_OLD` driven by a *follower's* clock rather than by a local write. (The
   local-write form of `RETRY_WRITE_TOO_OLD` **was** seen here — see §2.2 — so this row is
   narrower than it is usually stated, and the narrower version is the true one.)
3. **Cross-node latency**, and the wider contention window it opens on code that never
   loses a race over a loopback socket.
4. **The behaviour of the full demo-api suite against a multi-node cluster.** 557 tests
   have never been executed against one. Not once, by anyone, in this repository's history.
5. **Whether the `mainline-sql` role can even run the suite.** See §5 — this is a real and
   specific doubt, not a hedge.

**Nothing local stands in for any of the five.** A green from one node is a fact about one
node; this document does not offer it as anything else, and it may not be cited as though
it did.

## 4 · The exact lane, and the exact command

### 4.1 The lane — for the founder, who holds the credential

The lane exists and is committed: **`.github/workflows/cloud-verify.yml`**, job
**`cloud-demo-api-suite`**. It runs on the nightly `schedule` (17:00 UTC) and on
`workflow_dispatch`.

```
gh workflow run cloud-verify.yml --ref master
gh run watch
```

The job is written so that it cannot return green without having done the thing:

* It **fails by name** when `CRDB_CLOUD_DSN` is absent — it does not skip. A skip renders on
  the Actions tab as a grey tick indistinguishable from a lane that had nothing to do, and
  there is no second place in this repository where this suite meets a multi-node cluster.
* It **refuses a loopback DSN with an error**, never a quiet false — because the suite's own
  resolution ladder (`trappoint_testkit.cluster.reuse`) ends at `127.0.0.1:26257`, so a DSN
  that has silently fallen back to a local node would make every assertion pass while
  proving nothing.
* It **asserts nothing is listening on `127.0.0.1:26257`** inside the runner, so the last
  rung of that ladder is provably dead before the suite starts.
* It **counts executed tests and skips from the `--junitxml`**, never from the exit code,
  because `pytest` exits 0 when every test skips. The expected count is *collected from the
  checked-out tree seconds beforehand* rather than written down, so it cannot go stale.
* Any skip whose reason mentions an unreachable cluster — or refused migrations, §5 — is
  **fatal at a count of one**, regardless of the skip ceiling.
* No `continue-on-error`, no `|| true`, no defaulted return code.

Every one of those refusals was exercised against synthetic reports before the lane was
handed over; all seven fire, and the one legitimate green passes.

### 4.2 The command — if you are running it by hand

The suite reads its DSN from four environment names (`conftest.py:171`). Publish **all
four**: publishing three is how a run silently falls back to the fourth rung.

```sh
# Do not echo $CRDB_CLOUD_DSN, and do not paste it into a shell that logs history.
export MAINLINE_TEST_DSN="$CRDB_CLOUD_DSN"
export COCKROACH_URL="$CRDB_CLOUD_DSN"
export CRDB_URL="$CRDB_CLOUD_DSN"
export TRAPPOINT_DSN="$CRDB_CLOUD_DSN"

.venv/Scripts/python.exe -m pytest verticals/mainline/apps/demo-api/tests \
    --crdb=reuse -q -p no:cacheprovider --junit-xml=junit-cloud.xml
```

`-q` is load-bearing rather than cosmetic: `trappoint_testkit.plugin`'s
`pytest_report_header` prints the DSN it reused, and `-q` suppresses that header entirely
(measured — a `-q` run prints no `trappoint-testkit:` line at all). **Read the numbers from
`junit-cloud.xml`'s `testsuite` attributes, never from the terminal scroll.**

## 5 · What the first Cloud run is likely to hit — labelled as PREDICTION, not result

These are derived from code and from the captured fingerprint. **None of them has been
observed against Cloud.** They are written down so that the first run is read correctly
rather than read as a disaster.

1. **`CREATE DATABASE` or `CONFIGURE ZONE` refused with `42501`.**
   `conftest.py:797-802` issues `DROP DATABASE`, `CREATE DATABASE` and
   `ALTER DATABASE … CONFIGURE ZONE USING gc.ttlseconds = 4500` **unguarded**, as `root`
   would. The Cloud capture already records `mainline-sql` being refused `42501` for
   privileged reads. If either statement is refused, `conftest.py:806` turns the session
   into **skips**, and pytest exits **0**. That is the exact vacuity the lane's verdict
   refuses at a count of one.
2. **A wall-clock blow-out.** Every database the suite builds applies the whole committed
   migration chain plus the demo seeds, from a runner to Singapore rather than over
   loopback. The job's `timeout-minutes: 60` is generous and may still not be enough. **A
   timeout is a result worth having.** It is never answered with `-k`, `--deselect`, or a
   trimmed suite.
3. **Genuinely new `40001`s** in paths that have never lost a race locally — see §3(2).
   **This is the lane working.** A test that passes on one node and fails on a multi-node
   cluster is the finding this lane was built to produce.

that was hoped for. At the time of writing, the wave was **incomplete**:

recorded rather than the later one being silently substituted for the earlier — a status

|---|---|---|---|
| W1 | seed `mainline.defeater_option` | **NOT landed** | **STILL NOT landed** — `demo_world.sql` contains zero occurrences of `defeater_option` |
| W2 | resolve the vocabulary digest; refuse rather than fall back | landed | landed |

**The load-bearing row is W1, and it did not move.** `mainline.defeater_option` is still
empty, so §0's statement that this document reports no Cloud result and §3's list of what is

makes it evidence that the guard was needed, and W5's change is the response to it.

|---|---:|---:|---:|---:|---:|

Those failures and errors are almost entirely **one cause**: W2's refusal path is correctly

That is the wave half-applied, not a defect this document is reporting against Cloud — **and
no number in this file is a Cloud number.**

**The BEFORE/AFTER delta is not W6's, and the honest reading is spelled out rather than

609.9 s because **eight concurrent pytest processes** — four full-suite runs from four
different agents — were contending for the one local single-node CockroachDB. That is a
measurement artefact of a busy workstation, and it is recorded rather than presented as a
property of the code.

**One thing that wall time is genuinely worth noting for §5(2):** ten minutes is what this
suite costs when a single node is contended by four callers. A managed cluster in Singapore,
reached from a runner, is a different kind of slow — but it is a reminder that the 60-minute
budget on the Cloud job is not generous by accident.

## 7 · What result would FALSIFY the guards

Written in advance so the first Cloud run cannot be read after the fact to mean whatever is
convenient.

| observation against Cloud | what it falsifies | what it does NOT license |
|---|---|---|
| An uncaught `psycopg.errors.SerializationFailure` escaping a path W5 guarded | **the coverage claim** — that path's transaction is not wrapped whole, from `BEGIN` | wrapping a single `execute()`; `spec/errors.md` §2.1 calls that not-a-retry |
| `RetryBudgetExhausted` at `max_attempts=5` | **the POLICY, not the taxonomy** — Cloud's rate exceeds the budget | treating an undecided transaction as refused, or as success |
| A retry converges but the row counts are short | **the whole-transaction claim** — something replayed a statement into a poisoned transaction | patching the count; the shape is wrong, not the number |
| A SQLSTATE outside the modelled taxonomy (e.g. `40003`, or a `42501` the role cannot avoid) | **the taxonomy's completeness** | swallowing the unmodelled code; `UnmodelledRefusal` exists to surface it |
| The suite passes with **zero** `40001` observed | **nothing at all** | reading it as "the guards were unnecessary". It means the run was uncontended. A guard is justified by §2, not by whether it fired on one particular night |

The last row is the one most likely to be misread, which is why it is written down.

## 8 · Provenance
