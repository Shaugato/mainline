## 1 · What a multi-node CockroachDB does that a single node does not

A single-node `start-single-node` cluster and CockroachDB Cloud Basic run the same SQL and
the same isolation level. What differs is the set of *reasons* a transaction can be told to
start again, and how often it is told.

| | single node, this workstation | CockroachDB Cloud Basic (Singapore) |
|---|---|---|
| ranges | one replica, one store, one process | replicated across nodes |
| clock | one clock; there is nothing to disagree with | many clocks, bounded by `max_offset`; a read may land inside the uncertainty interval and be restarted |
| `RETRY_SERIALIZABLE` | produced by a **constructed** read-write cycle (§2) | produced by construction **and** by ordinary concurrent traffic |
| `RETRY_WRITE_TOO_OLD` | observed here, from a **local** write pushing a timestamp | also arises from a *follower's* clock, which has no local analogue |
| `ReadWithinUncertaintyInterval` | **not reachable** — there is no second clock | reachable, and it is a distinct restart reason |
| latency per statement | loopback, microseconds | a runner in `ubuntu-24.04` to Singapore, per round trip |
| contention window | narrow, because statements are fast | wider, because every statement is slower — the *same* code holds locks for longer |
| `gc.ttlseconds` | `14400` by default | `4500` — the local node is the **more permissive** exam |
| privileges | `root` | `mainline-sql`, already observed being refused `42501` (§5) |

The row that matters most is the second-to-last. Cloud does not mainly add *new* errors; it
widens the window in which the *existing* ones happen, so a transaction that has never lost
a race on a laptop can lose one routinely in Singapore. That is why "we never saw a `40001`
in CI" was never evidence that the retry loops were unnecessary.

> **THREE OF THOSE ROWS HAVE SINCE BEEN MEASURED RATHER THAN REASONED, AND THE TABLE IS LEFT
> STANDING BECAUSE ONE OF THE THREE CAME OUT NARROWER THAN IT READS.** Added 2026-08-14 by W1;
> the numbers are §9's and the artefact is `evidence/deploy/cloud-contention.json`. The table
> above states what CockroachDB *can* do, which is not the same claim as what it *did* here,
> and keeping both lets a reader see the gap.
>
> * **`RETRY_SERIALIZABLE`** — confirmed on Cloud, **12 races out of 12**, by construction. The
>   cell's second clause, *"and by ordinary concurrent traffic"*, is still **unmeasured**: the
>   one ordinary-traffic shape that was raced, `POST /v1/demo/gate-run` twice at once, produced
>   `40001` in **0 of 24** requests.
> * **`ReadWithinUncertaintyInterval`** — *"reachable"* is a statement about the platform and
>   remains correct; **it was not reached.** Twelve constructed races on Cloud produced none,
>   and neither did any request in Arm B. §9.4 says why that is an absence rather than a
>   refutation: this shape opens no uncertainty window.
> * **latency per statement** — measured from *this* workstation rather than from a runner, and
>   the multiplier is the finding: one attempt of the same race has a median of **0.4519 s** on
>   Cloud against **0.0024 s** locally (**≈188×**), and one whole `POST /v1/demo/gate-run` a
>   median of **17.84 s** against **1.64 s** (**≈11×**). **The contention window row is
>   therefore no longer an inference.**

### 2.1 A real `40001`, six of six, measured by W6 on this workstation

First message, verbatim and truncated:

This is an independent reproduction. The lead measured the same 6-of-6 under ruling R6, and
W4 measured it a third time over the product's own tables. **Three independent
reproductions on one node.** The claim that a single node "never produces" `40001` is
retired.

### 2.2 The guard is exercised by a control that fires — not by a mock

`docs/diagnosis/retry-negative-control.md` (W4) records the census over the product's real
seed-a-permit shape:

```
[control] unguarded census over 6 races: {'40001': 6, '00000': 6}
[control] guarded:                       12 commits, 6 retried 40001(s)
```

Unguarded, six of six races lost a whole history — a recall run, a Proof of Exhausted
Recall, an obligation, the exposure receipt and the line binding them. Guarded through
`trappoint_testkit.txn.run_txn` over `trappoint_core.retry.run_gate`, **twelve of twelve
callers committed** and the six `40001`s were *spied* being retried rather than assumed.
Re-run by W6 for this document:

```
pytest packages/trappoint-testkit/tests/test_txn.py \
       tests/concurrency/test_seed_permit_needs_retry.py --crdb=reuse -q

junitxml: tests=19  failures=0  errors=0  skipped=0  time=98.792s
```

W4 also observed **both costumes of `40001` locally** — `RETRY_SERIALIZABLE` and a
`WriteTooOldError`. Both carry SQLSTATE `40001`; a client discriminating on the *message*
would have got one of them wrong. `trappoint_core.retry` discriminates on the code.

### 2.3 The unguarded path flakes on ONE node, unprovoked

This one was not constructed. During W6's baseline run of the demo-api suite — no race
planted, no contention arranged — `_seed_permit` raised a real serialization failure:

```
verticals/mainline/apps/demo-api/tests/test_transitions.py:225: in _seed_permit
E   psycopg.errors.SerializationFailure: restart transaction:
    TransactionRetryWithProtoRefreshError: TransactionRetryError:
    retry txn (RETRY_SERIALIZABLE - failed preemptive refresh)
```

At the moment of that run `_seed_permit` committed roughly twenty-nine statements with **no
retry**. It had been predicted to "flake in the environment that matters"; it flaked in
**this** one, on one node, today.

**This is the strongest single argument in this document**, and it is an argument about
method rather than about CockroachDB. The guard was not added because a multi-node cluster
was imagined to need it — it was added because an unguarded transaction was **watched
losing a race on the machine that was supposed to be too simple to produce one**. W5 has
since wrapped it: `test_transitions.py:312` runs the whole transaction through
`trappoint_testkit.txn.run_txn` over `trappoint_core.retry.run_gate`, from `BEGIN`, on a
fresh connection per attempt — never a statement, which `spec/errors.md` §2.1 forbids. §6
records that W5 landed *after* the measurement above, which is the order that makes the
measurement evidence rather than decoration.

**And the repair is measured, not assumed.** Counting `_seed_permit` frames carrying a
`SerializationFailure` across the two `--junitxml` documents in §6:

```
BEFORE (11:17, unguarded) : 1
AFTER  (11:39, guarded)   : 0
```

One node, one unprovoked `40001`, one guard, and the error is gone from the report. **What
that does not establish is anything about Cloud** — see §3.

## 4 · The exact lane, and the exact command

### 4.1 The lane — for the founder, who holds the credential

The lane exists and is committed: **`.github/workflows/cloud-verify.yml`**, job
**`cloud-demo-api-suite`**. It runs on the nightly `schedule` (17:00 UTC) and on
`workflow_dispatch`.

```
gh workflow run cloud-verify.yml --ref master
gh run watch
```

The job is written so that it cannot return green without having done the thing:

* It **fails by name** when `CRDB_CLOUD_DSN` is absent — it does not skip. A skip renders on
  the Actions tab as a grey tick indistinguishable from a lane that had nothing to do, and
  there is no second place in this repository where this suite meets a multi-node cluster.
* It **refuses a loopback DSN with an error**, never a quiet false — because the suite's own
  resolution ladder (`trappoint_testkit.cluster.reuse`) ends at `127.0.0.1:26257`, so a DSN
  that has silently fallen back to a local node would make every assertion pass while
  proving nothing.
* It **asserts nothing is listening on `127.0.0.1:26257`** inside the runner, so the last
  rung of that ladder is provably dead before the suite starts.
* It **counts executed tests and skips from the `--junitxml`**, never from the exit code,
  because `pytest` exits 0 when every test skips. The expected count is *collected from the
  checked-out tree seconds beforehand* rather than written down, so it cannot go stale.
* Any skip whose reason mentions an unreachable cluster — or refused migrations, §5 — is
  **fatal at a count of one**, regardless of the skip ceiling.
* No `continue-on-error`, no `|| true`, no defaulted return code.

Every one of those refusals was exercised against synthetic reports before the lane was
handed over; all seven fire, and the one legitimate green passes.

### 4.2 The command — if you are running it by hand

The suite reads its DSN from four environment names (`conftest.py:171`). Publish **all
four**: publishing three is how a run silently falls back to the fourth rung.

```sh
# Do not echo $CRDB_CLOUD_DSN, and do not paste it into a shell that logs history.
export MAINLINE_TEST_DSN="$CRDB_CLOUD_DSN"
export COCKROACH_URL="$CRDB_CLOUD_DSN"
export CRDB_URL="$CRDB_CLOUD_DSN"
export TRAPPOINT_DSN="$CRDB_CLOUD_DSN"

.venv/Scripts/python.exe -m pytest verticals/mainline/apps/demo-api/tests \
    --crdb=reuse -q -p no:cacheprovider --junit-xml=junit-cloud.xml
```

`-q` is load-bearing rather than cosmetic: `trappoint_testkit.plugin`'s
`pytest_report_header` prints the DSN it reused, and `-q` suppresses that header entirely
(measured — a `-q` run prints no `trappoint-testkit:` line at all). **Read the numbers from
`junit-cloud.xml`'s `testsuite` attributes, never from the terminal scroll.**

those new tests meeting the same absent vocabulary. The wall time went from 35.6 s to
609.9 s because **eight concurrent pytest processes** — four full-suite runs from four
different agents — were contending for the one local single-node CockroachDB. That is a
measurement artefact of a busy workstation, and it is recorded rather than presented as a
property of the code.

**One thing that wall time is genuinely worth noting for §5(2):** ten minutes is what this
suite costs when a single node is contended by four callers. A managed cluster in Singapore,
reached from a runner, is a different kind of slow — but it is a reminder that the 60-minute
budget on the Cloud job is not generous by accident.

## 9 · CLOUD, MEASURED — the contention census of 2026-08-14

**Worker:** W1, cloud-hardening wave (`docs/leads/cloud-hardening-final.md`, rulings **R1**,
**R3**, **R4**, **R5**, **R10**). **Artefact:** `evidence/deploy/cloud-contention.json`.
**Program:** `scripts/deploy/cloud_contention.py`. **Conformance:**
`tests/concurrency/test_cloud_contention.py`.

This section reports the half §3 said was missing: the same race, driven by the same code,
against CockroachDB Cloud **and** against the local single node, **in one sitting**, so that
the difference between them is a comparison rather than two anecdotes taken on different days.

### 9.1 · The two arms

**Arm A — `constructed`.** Two rows in a scratch database the program `CREATE`s and `DROP`s.
Caller A reads key 1 then writes key 2; caller B reads key 2 then writes key 1, with a one-shot
`threading.Barrier` making both finish reading before either writes. The cycle is unorderable
by construction: whichever transaction the database picks to go second must be told to start
again. (**The barrier is for repeatability, not for the conflict** — removing it entirely still
gave 6 of 6, because the statements are sub-millisecond and two threads started together
overlap anyway. §9.5 records that, and records what *does* turn the signal off.) **It never
touches `mainline_demo`** — ruling R5, whose authority is that
`evidence/deploy/cloud-seed.json` publishes the demo's Cloud row counts as committed evidence
and a probe that moved one would falsify it.

**Arm B — `gate-run`.** Two concurrent `POST /v1/demo/gate-run`, each to its **own**
`scripts/deploy/local_furl.py` process — two processes, because `mainline_demo_api.db` caches
one psycopg connection at module scope and racing two requests through one cached connection
would be one connection used wrongly rather than two judges arriving together. This arm is
allowed against the live `mainline_demo` because the endpoint is savepoint-fenced and rolls
back; the permission is conditional on the ten tables the four beats can write being counted
before and after, **by the probe, over its own connection**, and they were.

**No topology was read.** `crdb_internal` and `system` are restricted for `mainline-sql` and
answer `42501`; contention is INDUCED and the SQLSTATE is observed (ruling R3). Every
connection named its database and confirmed it with `SELECT current_database()`; the committed
DSN's path segment says `defaultdb` and was never believed (ruling R10).

|---|---|---|
| rounds | 12 | 12 |
| callers | 24 | 24 |
| SQLSTATE census | `00000` × 24, **`40001` × 12** | `00000` × 24, **`40001` × 12** |
| restart reasons | **`RETRY_SERIALIZABLE` × 12** | **`RETRY_SERIALIZABLE` × 12** |
| where the `40001` surfaced | **`COMMIT` × 12** | **`COMMIT` × 12** |
| rounds producing a `40001` | **12 / 12** | **12 / 12** |
| `run_gate` actually retried | 12 callers | 12 callers |
| retries that converged | 12 / 12 | 12 / 12 |
| `RetryBudgetExhausted` | 0 | 0 |
| one attempt: min / **median** / max | 0.4448 / **0.4519** / 0.7351 s | 0.0020 / **0.0024** / 0.0121 s |
| `CREATE` / `DROP DATABASE` | 7.383 s / 1.565 s, **not refused** | 0.027 s / 0.296 s |
| scratch database proven gone | yes, `SHOW DATABASES` re-asked | yes, `SHOW DATABASES` re-asked |

**The headline is that every row down to the latency is identical, and the latency is not.**
Cloud did not produce `40001` more often than the local node under a race that is
deterministic by construction — a deterministic race is deterministic on both — and it did not
produce a different *reason*. What it produced was the **same verdict roughly 188 times more
slowly**, which is exactly the mechanism §1's second-to-last row named: Cloud does not mainly
add new errors, it widens the window in which the existing ones happen.

**Two rows are quieter than the latency and matter more to the guards themselves.**

*"Where the `40001` surfaced: `COMMIT` × 12"*, on **both** platforms, is the operational fact
this census turned up: under SERIALIZABLE the cycle is detected when the transaction is
committed, not when a statement runs. **A retry wrapper that guards `execute()` calls and not
the commit would have caught none of these twenty-four refusals** — which is `spec/errors.md`
§2.1's rule (*retry the whole transaction, from `BEGIN`, never a statement*) arriving as a
measurement rather than as a principle. §9.5 records that this probe had to learn it the
expensive way.

*"`run_gate` actually retried: 12 callers"* is read from the spy inside the loop, not inferred
from the fact that nothing blew up. Twelve of twelve retries converged on the next attempt and
**no caller exhausted the budget**, so on this shape `max_attempts = 5` is not close to being
the binding constraint on either platform.

### 9.2.1 · What the restart message itself said about the cluster — R3's method, paid back

**The most useful thing this census found was not a count. It was in the text.** Ruling R3
forbids proving multi-node behaviour by reading `crdb_internal` or `system`, on the ground that
`mainline-sql` is refused `42501` there and *"we could not read the node list"* is not a result
about ranges, replicas or clocks. **It turns out nothing needs to read them.** A `40001` message
volunteers the cluster's shape, and it volunteers it *because* a race was constructed.

Cloud, verbatim from `evidence/deploy/cloud-contention.json`, round 1, caller A, raised at
`COMMIT` — truncated only at the right-hand edge:

```
restart transaction: TransactionRetryWithProtoRefreshError: TransactionRetryError: retry txn
(RETRY_SERIALIZABLE): "sql txn" meta={id=83758f02 key=/Tenant/31219/Table/1526/1/2/0
iso=Serializable pri=0.00087610 epo=0 ts=1786700657.242688022,1 min=1786700657.242454960,0
seq=2} lock=true stat=PENDING rts=1786700657.242454960,0 gul=1786700657.492454960,0
obs={n6@1786700657.684826263,0} HINT: See: https://www.cockroachlab
```

and the local node, same round, same caller, same beat:

```
restart transaction: TransactionRetryWithProtoRefreshError: TransactionRetryError: retry txn
(RETRY_SERIALIZABLE): "sql txn" meta={id=2835eb44 key=/Table/57501/1/2/0 iso=Serializable
pri=0.02075764 epo=0 ts=1786700977.361204723,1 min=1786700977.360227827,0 seq=2} lock=true
stat=PENDING rts=1786700977.360227827,0 gul=1786700977.860227827,0
obs={n1@1786700977.360227827,0} HINT: See: https://www.cockroachlabs.com/docs/v
```

Three fields differ, every one of them structurally, and each is consistent across **all twelve
messages on each side**:

| field | Cloud | local | what it says |
|---|---|---|---|
| `obs={nN@…}` — clocks this transaction observed | **`n6`**, 12 of 12 | **`n1`**, 12 of 12 | the range was served by a node whose id is **6**. Ids are handed out in join order from 1, so **one process cannot produce this.** |
| `key=` prefix | **`/Tenant/31219/Table/…`** | `/Table/…` | Cloud Basic is **multi-tenant**; a local `start-single-node` has no tenant keyspace |
| `gul − rts` — the **clock-uncertainty window** | **0.25 s** | 0.50 s | Cloud runs a **250 ms** maximum clock offset; the local default is 500 ms |

**The third row is the one to read twice.** §3 item 2 has always been about restarts that happen
*inside* the uncertainty interval — the reason with no local analogue. This census did not
produce one, and it nonetheless **measured the interval**: it exists on Cloud, it is 250 ms
wide, and it is **narrower than the local node's**, which is the opposite of the way the
trade-off is usually assumed. A local node is the *more permissive* exam on clock skew for the
same reason §1 already records it is on `gc.ttlseconds`.

**The first row is a fact about topology obtained without a topology query**, which is exactly
what R3 asked for. It is also carefully bounded: `n6` says a node numbered six served this
range, **not** that six nodes are running now, and this document does not make the second claim.
`tests/concurrency/test_cloud_contention.py::test_the_restart_messages_themselves_distinguish_the_two_clusters`
recomputes all three from the committed artefact, so none of them can drift into prose.

### 9.3 · Arm B, side by side — and the prediction it FALSIFIED

| | **Cloud / `mainline_demo`** | **local / `w_w1_demo`** |
|---|---|---|
| rounds (2 concurrent POSTs each) | 12 | 12 |
| HTTP statuses | `200` × 24 | `200` × 24 |
| verdicts | **`PROVEN` × 24** | **`PROVEN` × 24** |
| `persistence_check.identical` | **true × 24** | true × 24 |
| `self_persisted` | false × 24 | false × 24 |
| requests that saw a **concurrent write** | **0** | **0** |
| `outcome: retry` (a `40001` on the demo path) | **0 of 24** | 0 of 24 |
| one request: min / **median** / max | 17.38 / **17.84** / 18.29 s | 1.19 / **1.64** / 2.07 s |
| the ten fingerprint tables, before vs after | **byte-identical** | byte-identical |
| Cloud counts still equal `cloud-seed.json` | **yes** | n/a |

**The wave's plan predicted that this arm would answer `NOT PROVEN`, and called that W1's most
valuable single result. It did not, and the reason is worth more than the prediction was.**

`docs/leads/cloud-hardening-final.md` §0.1.1 reasoned that `_FINGERPRINT_SQL` counts whole
tables, so two runs racing each other would see each other and one would accuse itself of a
write it had not made — *"two judges pressing the button at the same moment is precisely this
interaction."* **Twelve rounds of exactly that, against the live Cloud database, over HTTP,
from two separate operating-system processes, produced twenty-four `PROVEN`s and zero observed
concurrent writes.**

**Two gate runs cannot falsify each other, because neither commits anything.** The mechanism
needs a writer that COMMITS a row into one of the ten tables between a run's two readings, and
a gate run is not one. W2 reached the same conclusion independently and first, in-process and
on one node — `docs/diagnosis/gate-run-fingerprint.md` §0(4) and §2 — and **named the actual
writer**: concurrent `pytest` sessions sharing one scratch database, whose `test_transitions.py`
fixtures had committed 677 `PTW-W4-*` and 102 `PTW-BARE-*` permits at up to four per second.
§9 is the Cloud confirmation of that falsification, at a different concurrency level, through a
different transport, on the platform the demo actually runs on.

**This is not evidence that the defect was unreal.** It is evidence that *"two judges"* was the
wrong story for a real defect, and the difference matters because the wrong story suggests the
wrong repair. A judge cannot cause it; a second test session can.

**One caveat is stated rather than left to be discovered.** This arm ran against the working
tree of 2026-08-14, in which W2's separation of `identical` (did the DATABASE move) from
`self_persisted` (did THIS RUN persist anything) had already landed, so the verdict no longer
keys on the unscoped counts. That change cannot account for the result above, and the reason it
cannot is the sixth row: **`identical` was `true` in all twenty-four requests and no concurrent
write was seen at all.** Had the pre-change handler run this arm, it would have keyed on that
same `true` and answered `PROVEN` too.

**What this hands to whoever owns `gate_run.py`.** Three things, none of them a request to
change anything:

1. **The falsification now holds on Cloud**, not only on one node in one process. If W2's
   diagnosis is ever re-argued, this is the second, independent measurement of its central
   claim, taken through HTTP and across process boundaries against the live database.
2. **The demo is safe from the failure mode in front of judges.** Two people pressing the
   button together is measured, twenty-four times, on the platform the demo runs on, and it
   answers `PROVEN`. The residual risk is a *committing* writer — which on Cloud means
   `seed_demo.py`, `cloud_chain.py` or a second operator, not a visitor.
3. **The window is much wider on Cloud than the local reproduction suggests.** One gate run
   takes ≈18 s against Cloud versus ≈2 s locally, so the interval in which a foreign commit
   *could* land between the two fingerprint readings is roughly nine times longer in
   production. That does not change the verdict logic; it changes how often the
   `concurrent_writes` field will be non-null in the field, and it is the number to keep if
   anyone later asks how likely the reported-but-not-blamed case is.

### 9.4 · What §9 does NOT license

Written here rather than left implicit, because every number above is easier to over-read than
to read.

* **`0 of 24` `40001`s in Arm B does not mean the retry guards are unnecessary.** §7's last row
  fixed that reading in advance and it is not revised now that a run has produced a zero: it
  means the run was uncontended in the way that matters, not that contention cannot happen.
* **No `ReadWithinUncertaintyInterval` in twelve races does not mean Cloud cannot produce one.**
  Arm A holds no read across a follower and opens no clock-uncertainty window; it is a
  read-write cycle on two keys. The honest statement is *"this shape did not produce one"*, and
  the item stays on §3's list, narrowed rather than closed. **§9.2.1 sharpens the item rather
  than settling it**: the window is real and is 250 ms wide, so what is missing is a *shape*
  that lands inside it, not a platform that has one.
* **`obs={n6@…}` is not a node count.** It is a node **id**, from the observed-timestamp set of
  one transaction. It rules out a single-node cluster and it does not establish how many nodes
  are serving today.
* **12 / 12 on both platforms does not mean Cloud and local are equivalent.** It means a
  deterministic race is deterministic on both. The rate that item 1 of §3 asks about is the
  rate under *ordinary* traffic, and one endpoint's `0 of 24` is a bound on one endpoint.
* **§9 says nothing about the demo-api suite on a multi-node cluster.** That is §3 item 4 and it
  is still zero.

### 9.5 · What §9 would have shown if the guards were wrong

`evidence/deploy/cloud-contention.json` records, per caller, both what the `run_gate` spy saw
and what the server said, and the two are required to agree. During development they did not —
and the disagreement was a defect in **this probe**, not in the guards:

> The probe's first recorder wrapped the SELECT and the UPDATE in `try/except` and left the
> commit unwatched. Under SERIALIZABLE, CockroachDB detected the cycle at **`COMMIT`** — all
> twelve of twelve, on both platforms, as the table in §9.2 now records — so `work` returned
> cleanly, `run_txn` committed, the commit raised `40001`, `run_gate` retried it, and the census
> printed **`rounds_with_40001: 0`** for a round the spy had recorded a retry in.

The spy was right and the hand-rolled recorder was wrong, so **the recorder moved**. That is the
tiebreaker applied to the probe's own two halves. The failure is frozen in
`tests/concurrency/test_cloud_contention.py::test_the_census_counts_a_40001_that_surfaced_at_commit`,
which feeds the census an arm in exactly that shape and requires the count to be one; run
against the original recorder it reads zero. The per-caller agreement check is now a refusal
in the program itself, and a disagreement makes the run exit non-zero rather than publish.

**And the race itself has a control that turns it OFF**, because an instrument that answers
`40001` whatever it is pointed at is answering nothing. Same threads, same rendezvous, same
`run_txn`, same scratch database, same round count — and two callers whose transactions touch
**disjoint keys**:

| shape | keys (A / B) | rounds with `40001` |
|---|---|---:|
| the measurement (`CYCLE`), 12 rounds, both platforms | read 1 → write 2 / read 2 → write 1 | **12 of 12** |
| **the control** (`DISJOINT`), 6 rounds, local | read 1 → write 1 / read 2 → write 2 | **0 of 6** — twelve clean commits |

Six rounds rather than twelve because this is a control on the instrument and not a census of a
platform; it lives in the test suite, and §9.7 says so rather than letting the two row lengths
look like a comparison.

**Two weaker controls were tried first and BOTH failed to discriminate**, and they are recorded
because the obvious next person will try them too:

* **removing the rendezvous entirely still gave 6 of 6.** The statements are sub-millisecond,
  so two threads started together overlap whether or not a barrier says so. The barrier makes
  the race *repeatable* rather than scheduling-dependent; on this shape it is not what causes
  the conflict.
* **pointing both callers at one single key still gave 6 of 6.** Two concurrent
  read-modify-writes of one row are unorderable for the same reason a two-key cycle is, so
  "no cycle" was not what that change produced.

**Only disjointness turns the signal off.** Both shapes are constants in the program
(`CYCLE` and `DISJOINT`) and both are asserted in
`tests/concurrency/test_cloud_contention.py`, so the control cannot rot separately from the
measurement.
